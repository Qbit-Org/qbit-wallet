# @qbit/wallet-state

## 7.0.0

### Major Changes

- de2dce5: Remove the wallet and account rename screen hooks, which the account switcher replaced (#177): the extension renames a wallet or an account in a dialog over the switcher, calling `setKeyringAlianName` and `setAccountAlianName` and dispatching `keyringsActions.updateKeyringName`, `keyringsActions.updateAccountName` and `accountActions.updateAccountName` itself. `useEditWalletNameScreenLogic` and `useEditAccountNameScreenLogic` are no longer exported, and `RouteParamList` drops `EditWalletNameScreen`, `EditAccountNameScreen` and `SwitchAccountScreen`, whose screens are gone.

  `useExportMnemonicsScreenLogic` returns `hdPath`, the path `getMnemonics` returns with the phrase (empty when it returns none), and works out `pathName` from it rather than from the listed keyring, whose path is empty when the wallet is corrupted. An answer without a phrase fails on the password step, with an error, instead of reaching the phrase step.

  `useExportMnemonicsScreenLogic` and `useExportPrivateKeyScreenLogic` return `handleOnKeyDown` in place of `handleOnKeyUp`: Enter submits the password on its keydown in the field, never on a keyup, a held key's repeats or the Enter that ends an input method's composition, so the Enter that opens either screen from the account switcher submits nothing. Both now follow `isEnterPressedInField(event)`, which the package exports for any field that submits on Enter: true for an Enter pressed in the field, false for a held key's repeats and for the Enter that ends an input method's composition.

- de81656: Remove the notification and announcement state, which only ever held empty lists. `useNotificationsLogic`, `useUnreadNotificationsCount` (and the 3-second poll behind it), `useAnnouncementCardLogic`, `StorageContext`, `useStorage`, `createStorageProvider` and the `StorageContextType` type are no longer exported. The `WalletController` interface drops `openapi`, `getBlockActiveInfo`, `getAnnouncements`, `getNotifications`, `readNotification`, `readAllNotifications`, `deleteNotification` and `getNotificationUnreadCount`, and `RouteTypes` drops `NotificationListScreen`. The settings state's `walletConfig` no longer has `moonPayEnabled` or `endpoint`.
- de81656: Remove the signData and deriveContextHash approval screens, the developer-mode setting that allowed signData requests, and the background methods behind them. No provider method opened either screen. Breaking change: `WalletController` no longer has `getEnableSignData`, `setEnableSignData` or `deriveContextHash`, and `UI_CONTROLLER_METHODS` no longer lists the first two, so `getUiControllerMethod` refuses them. `PreferenceService` no longer has `getEnableSignData` or `setEnableSignData`, and `BasePreferenceStore` no longer has `enableSignData`. A stored `enableSignData` value is dropped when the preferences load and is not saved again. In `@qbit/wallet-state`, the `WalletController` interface no longer declares `getEnableSignData` or `setEnableSignData`.
- de81656: Remove the `useModelPopover` hook, the `accountActions.setModelPopover` action and the `molelsPopover` field of the accounts state, so `AppState['accounts']` no longer has it. Nothing called the hook or dispatched the action. Only the `ui` slice is persisted, so stored state is unaffected. The internal `getAddressUtxoDust` helper, which had no callers, is removed too.
- de2dce5: Add `setKeyringColor(keyring, color)` to the `WalletController` interface, and `keyringsActions.updateKeyringColor`, which sets the color of the wallet it is given in the current wallet and the wallet list (#177). The placeholder wallet before the first load has a palette key too. The restore flow's word step no longer suggests "HD Wallet #N" as `walletName`, which nothing read: the background names a wallet when it adds it. With that, the `WalletController` interface drops `getTotalKeyringCount`, which nothing else called. `RouteParamList` drops `CreateAccountScreen`, whose screen became a dialog over the account switcher (#177).

### Minor Changes

- de81656: `useSignPsbtLogic` signs each entry of a local batch, quick-signed or reviewed on its own, as a member of the batch the wallet opened for the reviewed approval, and returns `signatureBatchBudget`, the whole batch's signature budget, for the approval to show in place of each entry's own before and after figures, which depend on the signing order (#152).
- 34f14f2: Let the consolidation screen choose how many outputs each batch merges (#170). `useQbitConsolidationScreenLogic` holds the batch size as typed (`batchSizeText`, `onBatchSizeChange`, `onClickBatchSizeMax`) and opens at the account's maximum, `QbitConsolidationStatus.maxInputCount`, 106 single-key inputs. It accepts only digits naming a whole number from 2 to that maximum, checked with `isQbitConsolidationBatchSize`, the rule the background applies to the request; anything else disables Prepare and sets `batchSizeError`. The size goes with the request as `maxInputs`, the maximum included, and it is part of what a batch was prepared for: a batch prepared at another size is dropped, and a prepare still running for one is never published. Until the status loads there is no maximum to check a size against, so no size is offered. A batch prepared after a failed status read carries the size the route names when it could be one (a whole number of at least 2), which the background checks against its maximum and refuses with a readable error when it is past it, or none, and the background uses its maximum; once the status loads, a batch prepared at that size stays. A route's size can be past the maximum when the maximum is lower for the account or version the screen opens on than for the batch the size came from. While the maximum is unknown, a prepare that fails reads the status again, as one that succeeds always does, so a status that loads then gives the screen its maximum, and a route's size past it gives way to the maximum; once the maximum is known, a failed prepare reads no status. The size, its range, the fee preview and the cost note are offered only for an account over the limit. `feePreview` gives the fee and size of a full batch of the chosen size at a settled rate (`estimateQbitP2mrTransaction` on `QbitConsolidationStatus.batchShape`), and `costNote` how much more in fees smaller batches take than the largest, in whole percent; both stay empty without a batch shape. A failed status read or prepare now shows its message: the wallet proxy rejects with a plain `{ message, stack }` object, which the screen showed as "[object Object]".

  The next batch keeps the size. `useTxConfirmScreenLogic` passes the batch's `QbitConsolidationBatch.maxInputs` to the success screen as `consolidationMaxInputs`, and Consolidate next batch opens `QbitConsolidationScreen` with it as `maxInputs`. The screen checks that value against the current maximum and opens at the maximum when it is missing or out of range. Back from the confirm screen keeps the size chosen too: before it opens the confirm screen, the consolidation screen writes the batch's size with the account's network and address into its own route state, and it opens at the maximum for another account or network. A size the user types likewise applies only to the account and network it was typed for: the screen holds one typed size, not one per account, so another account or network opens at its own opening size, and once a size is typed there, switching back opens the first at its opening size. A batch that reaches the success screen through the failure screen's Retry or Check status still offers the next batch at its size: `useTxConfirmScreenLogic` passes `consolidation` and `consolidationMaxInputs` to `TxFailScreen` as well, and `useTxFailScreenLogic` hands them on. The confirm, failure and success screens check them the same way: only `consolidation: true` marks a batch, and only a safe integer is passed on as its size. `RouteParamList.QbitConsolidationScreen` takes the optional `maxInputs`, `chain` and `address`, `RouteParamList.TxFailScreen` the optional `consolidation` and `consolidationMaxInputs`, a route whose params are all optional can now be opened without any, and `WalletController.createQbitConsolidationPsbt` takes a `QbitConsolidationRequest`.

  After the explorer refused a transaction as too large to broadcast (`too_large`), `useTxFailScreenLogic` offers no Retry (`canRetry` is false) whatever the outcome, since the explorer refuses the same bytes the same way; Check status stays for an unknown outcome.

- f755b4e: `useQbitConsolidationScreenLogic` takes whether the account is over the explorer's listing limit from the status's `overLimit`, the explorer's own answer, instead of comparing its count with the limit, and no longer estimates the batches left, at the account's maximum or at a chosen batch size (#169): electrs keeps refusing an address that once held more outputs than its limit, so consolidating does not make the explorer list it again; only the operator raising the limit does. The status line names the limit only when the explorer's refusal states one (`consolidation_status`, or `consolidation_status_no_limit`), whatever the batch size, the new `refusalText` (`consolidation_refusal_lasts`) says, when the refusal names a limit or the wallet assumes 500 for a bare HTTP 500, that it lasts until the operator raises that limit, and `consolidation_within_limit` takes no limit. `useTxCreateScreenLogic` returns the send screen's consolidation note as `consolidationNote`, empty once the account's outputs could not be read from its history either, since the note says that sends read them from there. The extension shows the refusal line on the consolidation screen and drops `consolidation_status_confirming` and `consolidation_status_counts`. In all six locales, the send screen no longer says that consolidating lets the account send and migrate normally again, and says that reopening Send tries a failed history read again (`consolidation_send_note`, `utxo_limit_exceeded_send`); the recovery screen no longer asks the user to consolidate a deferred account until the explorer lists it (`qbit_recovery_deferred_history_too_large`); and neither the balance card nor the recovery screen blames too many outputs for a refusal that can outlast them (`utxo_limit_exceeded_balance`, `qbit_recovery_deferred_history_incomplete`).
- 3f369b4: Take fee rates from qbit Core's relay floor of 0.25 bits/vB on the send and consolidation screens (#182). `useFeeRateBarLogic` returns `minFeeRate`, the lowest rate the Custom input offers, which is `QBIT_MIN_RELAY_FEE_RATE` in every state; `supportLowFeeMode` is still returned but no longer decides it. `adjustFeeRateInput` keeps a rate as typed: it no longer raises a Custom rate below 1 bit/vB to 1 (or one below 0.1 to 0.1 in low-fee mode), nor replaces a zero with the default rate, so a rate still being typed, such as "0." or "0.2", stays in the input while Next stays disabled, and the screens refuse a rate below 0.25 as they refuse one above the ceiling. For a Custom rate typed below 0.25, `useTxCreateScreenLogic` and `useQbitConsolidationScreenLogic` also say why in their `error`, with the new `fee_rate_below_minimum` message naming the floor, by one decision both screens share (`feeRateBelowMinimumError` beside `feeRateOrigin`): the typed text decides, so a zero that is no longer being typed ("0.0", "0.00", "00") gets the message as "0.1" and "0.24" do, while an empty input, "0" and "0." (still being typed) and a tier's rate get none; the consolidation screen gives it only while it has a batch to prepare, and prepares none while it shows it. Text that is not plain decimal digits, such as a pasted "0,25", "1e3" or "-1", clears the input instead of being read as another rate. Tiers below 1 bit/vB are selected at their own rates, and typing the selected tier's rate keeps the tier. Without estimates the rate in use is `QBIT_FALLBACK_FEE_RATE` (1 bit/vB), not the floor: after a failed read the bar writes it to the store, shows it in the input and starts a Custom rate from it, `fallbackFeeRate` is that rate, and a tier of a quote without estimates is recognised by it; a Custom rate down to 0.25 is still accepted there. The fee-bar store's initial rate and the placeholder review's `recommendedFeeRate` now name `QBIT_FALLBACK_FEE_RATE`, still 1. Low-fee mode's fixed slow rate is the relay floor instead of 0.1 bits/vB. The `above_relay_floor` warning gives its multiple of the 0.25 bits/vB floor, so 100 bits/vB reads as 400× the network minimum. The new `formatFeeRate` export shows a fee rate as the screens and the fee warnings show it: rounded down to hundredths, so a rate shown is never higher than the rate paid (936 bits for 3,817 vB, 0.2452 bits/vB, shows as 0.24, not as 0.25), a rate already in hundredths as it is, a positive rate below 0.01 as "<0.01" and one that is no finite number of 0 or more as "-"; the fee warnings use it in place of rounding to the nearest hundredth.
- 5d6305f: `TabOption` gains `'mine'` and `RouteParamList` gains `MineTabScreen`, for the extension's new Mine tab.
- 002b24e: A payment that needs more of an account's outputs than one transaction can carry is sent as one plan the user confirms once. The send screen prices it with `planQbitSend` on the outputs and shape its preflight uses (`planQbitP2mrSendPreflight`) and shows what will happen instead of refusing: the transactions that combine the funds, then the payment, the total fee, exactly what the recipient receives, the signatures and about how long signing takes. MAX sends the most the account can send now: the plan of its confirmed outputs, which pays their whole balance less every fee and says that funds not confirmed yet are not included, only when it pays the recipient more than one transaction of the largest outputs can now (`qbitP2mrSendAllSendableSatoshis`); otherwise, a tie included, MAX sends that one transaction as before. When the balance covers the amount but not every fee, or the amount needs more transactions than one plan carries, it says so and offers the largest amount that can be sent as a choice, never in its place. While the account has a plan in progress (any phase but completed, as `useQbitSendPlan` reads it), the background starts no other: MAX then sends one transaction of the outputs that plan does not hold, with the note of what stays and a line that a payment in progress holds the rest, linked to it; an amount only a plan can pay keeps Next disabled with the payment in progress named and linked; a refusal offers only what one transaction sends. The send screen reads the outputs again when that plan starts, changes its transactions or ends, and reads the plan again when Next is answered `plan_open`. `useQbitSendPlanReviewScreenLogic` holds the one review and its one confirmation, with the restored-floor confirmation before the plan starts and a review that expires; `useQbitSendPlan` follows the selected account's plan on the active network (on mount, on `QBIT_SEND_PLAN_CHANGED`, on account and network changes, and every five seconds while it is open), drops a view older than one shown and never shows a plan for another account or network; `useQbitSendPlanScreenLogic` and `useQbitSendPlanEntryLogic` drive the progress screen, whose buttons are exactly the actions the plan offers and which shows the recipient, the amount and the total fee with its rate in every state of a readable plan, so the terms the user confirmed are in view before Continue, and the home screen's card. While a version of the payment that left the wallet without an answer may still confirm (`paymentMayConfirm`, read only as `true` or absent, and never of a plan paused `unreadable`), both say so whatever the plan paused for or is doing: the payment may still go through, the wallet keeps checking, the recipient is not to be paid another way until that is settled, what the user can do (only the actions the plan offers: raise its fee, send the same payment again) and that the funds it uses are in the wallet, held for it; no copy then says that nothing was sent, that the payment was not sent, or that it can be cancelled or reviewed again. `WalletController` gains `prepareQbitSendPlan`, `startQbitSendPlan`, `getQbitSendPlan`, `continueQbitSendPlan`, `cancelQbitSendPlan` and `dismissQbitSendPlan`, the routes `QbitSendPlanReviewScreen` and `QbitSendPlanScreen` are added, `TxSuccessScreen` takes the `sendPlanId` of a completed plan to remove once the user leaves, and `usePrepareSendQBTCallback` takes a fresh `utxoSnapshot`. A fee raise at a rate too low to replace what was sent names the lowest rate that works (#188).
- 6bcab59: Keep the send form out of `localStorage`, and clear it when the account or network changes (#197). `createAppStore()` saves only the display preferences `isBalanceHidden` and `balanceDetailExpanded`, still under `redux_localstorage_simple_ui` and still through redux-localstorage-simple, as a JSON object of those two fields, a second after an action that changed one of them; an action that changes neither writes nothing, so a page no longer puts its older preferences back over a change another page saved unless it changes one itself. The store loads only those two from the saved value, so the rest of the `ui` state starts at its initial values. As the store is made, a saved value that holds anything else, such as the whole `ui` state with the send form that earlier builds saved, or no JSON object at all, is replaced at once with the two preferences alone, or removed when it cannot be replaced, and a preference that is not a boolean of the saved object's own takes its initial value; a value that holds just the two is left as it is, and a missing one stays missing. The send form (`uiTxCreateScreen`), the fee bar (`feeRateBar`), `addressInput` and `amountInput` stay in the store while the page is open, and take their initial values in the same store update in which the selected account (`accounts.current.address`) or network (`settings.chainType`) changes from one known to another; nothing is cleared while the store has no account (an empty address), nor when the same account and network come back, as after a lock and an unlock or a read of the same account. The `ui` state's new `sendFormScope` records the account and network the form's values were entered under. `useTxCreateScreenLogic` returns `formKey`, a new key for each scope the store records (the first account and network known, which clears nothing, and each clear for another account or network, also for one that comes back), for an input that keeps its own copy of a value to be keyed on, and reads the saved replace-by-fee choice again when the key changes, as a newly opened form does; a read sets the form's choice only if no later read has started and the user has not changed the choice since it started. A send that `onClickNext` prepares is dropped when, before it is built or refused, Next is clicked again, the screen is left, or the store clears the form for another account or network: it opens no confirm screen and sets no error, so only the latest Next of a mounted form does either.
- 5d1f01d: Show the progress of a local signing (#171). `useSigningProgress()` follows the signings a page starts: `start(transaction?)` hands out the `progressId` to pass to the signing call, `progress` holds the inputs signed, their total, the transaction of a batch and, once three new signatures are timed, the time left (cached signatures, which come back at once, are not counted in the rate), and `stop(id)` ends it. Only that signing's events show. `useSignPsbtLogic` passes a `progressId` to every local signing and returns `signingProgress` and `signingInputCount`. A Sign press while a local signing runs signs nothing (#34). A single transaction handed to its broadcast or approval keeps `isPsbtSigning` set until its screen goes away. If the approval refuses the result, the screen gets its Reject back, and `currentSigned` (now returned) keeps Sign disabled, since the result's claim is still held. A quick-signed batch closes the disclaimer as it starts, runs one at a time, and stops at a lock. The broadcast after signing names its step (`broadcasting_transaction`).
- 5e032b2: `useWebsiteSafetyCheck()` and `useConnectWebsiteCheck()` accept a `clear` verdict with reason `trusted` and return `trusted`, which is true only while such a verdict is the current one; one that arrives after the check timed out does not count. `useSignMessageLogic()` and `useSignPsbtLogic()` return it as `isTrustedWebsite`. The extension's connect and signing screens show "Official Qbit website" for it, and a batch from that site can be signed at once without the per-site opt-in.

### Patch Changes

- de81656: Drop the code paths for a chain that is not a Qbit chain. Every chain the wallet can select is a Qbit chain, and `normalizeChainType` now accepts only a string that `CHAINS_MAP` defines as its own key. A stored or requested chain that names a property every object inherits, such as `constructor`, `__proto__` or `toString`, and a value that is not a string but converts to a chain name, such as an array (`['QBIT_REGTEST']`) or a String object, now normalize to Qbit Mainnet like any other unknown value, through `normalizeChainType` and `normalizeAvailableChainType` alike, instead of passing through as a chain. `PreferenceService` therefore loads such a stored chain as Qbit Mainnet, so a stored `['QBIT_REGTEST']` can no longer select the local regtest endpoint at startup without the background's regtest check.

  Breaking change in `@qbit/wallet-shared`: `COIN_DUST` is removed. The send screen's dust limit is `QBIT_P2MR_DUST`.

  In `@qbit/wallet-background`, the `WalletController` methods that refused a chain that is not a Qbit chain no longer check for one: the history, raw transaction and lifecycle reads, the restore floor scan, recovery migration, receive and consolidation. The checks of a chain that a request names, in send claims, broadcast identities, external signing locks and fee bumps, stay. `restoreQbitKeyringWithFloors` refuses an address type other than P2MR, `getQbitConsolidationStatus` refuses an account without a P2MR script, and `getAddressCacheHistory` always reads the account's own history (`[]` for an empty address). `signPsbtV2` always checks a PSBT's inputs against the send guards before it signs. `createKeyringWithColdWallet` and `deriveAccountsFromXpub` refuse with `hardware_wallet_not_supported` without reading their arguments, as they already did on every Qbit chain (#53); a stored cold-wallet keyring still loads. `wallet-background` no longer imports `bitcore-lib`.

  In `@qbit/wallet-state`, `useTxCreateScreenLogic` always applies `QBIT_P2MR_DUST` and the relay fee floor, and treats an account with a P2MR script as a P2MR send; `useFeeRateBarLogic` always keeps a typed rate above `QBIT_MAX_FEE_RATE` for the send screen to refuse.

- de81656: Adding or editing a contact no longer clears its alias flag or silently replaces another contact. `updateContact`, `addContact` and `replaceContact` now take `isAlias` as optional: left unset, the stored entry keeps the alias flag of the entry already under the contact's address and chain, and a contact stored at an address with no entry gets `false`. A caller that sets `isAlias` still decides it. `addContact` is no longer the same as `updateContact`: it rejects with `ContactAlreadyExistsError` (`code` `CONTACT_ALREADY_EXISTS`) and changes nothing when a contact is already stored under the address and chain. `replaceContact` rejects the same way when another contact is stored under the new address and chain. Both check the store at the time of the write, so a screen that loaded before that contact was added cannot overwrite it. Address matching is exact, as in the stored key. Adding at an alias-only entry, editing a contact under its own address and chain, and moving it onto an alias-only entry all still save. `updateContact` still writes over the entry under its key. The wallet controller's `addContact` is now open to the wallet's own pages. The add and edit screen (`useEditContactScreenLogic`) no longer sends `isAlias`. It adds with `addContact`, moves with `replaceContact` and saves in place with `updateContact`. Before an add or a move, it checks the address, and in that case or when the contact book refuses, it shows "Another contact already has this address on this network" instead of saving. The message clears when the address changes.
- de81656: `useCreateAccountCallback` and `useRestoreQbitWalletCallback` mark the wallet unlocked only if the background still reports it unlocked once the create or restore returns, so a lock that came in meanwhile is not overwritten and the wallet is not shown unlocked over a locked background.
- eb21918: A page that loaded before the wallet existed now goes to the unlock screen when the wallet locks (#198): `AccountUpdater` asks at every lock whether a vault exists and marks it in the store (`isBooted`), and `useCreateAccountCallback` and `useRestoreQbitWalletCallback` mark it once they return, or once they fail with the wallet locked and a vault saved. Only a vault found is marked, never its absence, and a read that fails changes nothing.
- de81656: `useSecurityCardLogic` backs the two new Security switches, "Lock when the computer locks" and "Lock when all windows close": it reads both settings, saves one change at a time, and keeps a switch as it was when its change is not saved, with the same error messages as the other security settings. The `WalletController` interface gains the four lock-setting methods.
- de81656: Remove the `useInfiniteList` hook (`src/ui-hooks/useInfiniteList.ts`), a source file nothing imported. The package's entry points (`.` and `./types`) never reached it, so what the package exports is unchanged.
- de81656: Fill every field that a saved `ui` state lacks when the wallet loads it. The `updateVersion` handler now gives the state saved by an earlier build each field of the current initial state that it is missing, at every depth, and keeps the values it saved. Before, a saved state without `addressInput` or `amountInput` made `updateAddressInput` or `updateAmountInput` throw, and a fee bar or send screen missing some fields stayed incomplete. Releases 1.0.5 to 1.0.7 start every new state with both fields, but kept a state that an earlier build saved without them as it was. A field that should hold an object but holds something else is replaced with its initial value, and a saved state that is not an object loads as the initial state.

## 6.0.0

### Major Changes

- eb9f779: Check each recovery phrase word while it is entered (#76). `useCreateWalletLogicImportWordsStep` returns `inputWordsInvalid`, one flag per input that is true when the input holds a word that is not in the English word list, and `inputWordsError` is now true only when every word is entered and in the list but the phrase still fails `validateMnemonic`. It also returns `pastedTooManyWords`, true after a paste with more words than the inputs from the paste point onwards, whose extra words were dropped; the next typed change, a paste that fits, or a switch between 12 and 24 words clears it. Switching between 12 and 24 words also clears `inputWordsError`. The per-word check uses an internal helper next to `validateMnemonic` that accepts a word exactly when that check would: it applies the same Unicode normalization and compares case-sensitively against the same list. What Continue accepts and the phrase passed on are unchanged. Breaking change: `inputWordsError` is no longer true for a complete phrase that contains a word outside the list, so code that relied on it for that case must read `inputWordsInvalid`.

### Patch Changes

- eb9f779: Show the balance as unknown (`--`) instead of 0 until a balance read for the current account and network has succeeded. Until then `useAccountBalance` returns zeros tagged with the current network, so the balance card showed `0.00000000`, kept showing it while every read failed, and the send screen showed Available as 0. `useBalanceCardLogic` now sets `isCurrentChainBalance` only once a read for this account on this network is stored; before that, `balanceValue`, `availableAmount` and `unavailableAmount` are `--`, and `availableBalance` and `unavailableBalance` are `null`. `useTxCreateScreenLogic` shows Available from the balance figure as `--` until such a read, as it already did for a figure the explorer's limit leaves unknown, and shows the Unavailable, Immature and Pending rows as `--` rather than hiding them. A 0 that a read returned still shows as 0. `balanceSplitUnknown`, and with it the note naming the explorer's limit, now applies only when the read reports the account over that limit (`utxoLimitExceeded`), not to a split unknown for another reason.
- eb9f779: Stop losing a contact when changing its address or network fails to save. The new `ContactBookService.replaceContact(address, chain, data)` removes the contact under the old address and network and stores `data` in one write. The result is the one `removeContact` followed by `updateContact` gave, except that the contact keeps its place in the list: an old entry that is also an alias stays as an alias, the new entry is stored where the old contact was, with the given `sortIndex` or else the old contact's, and an entry already stored under the new address is replaced. A failed write rejects and leaves the original contact in place, in memory and on disk. The stored contact book keeps its key and shape. The wallet controller's new `replaceContact` is open to the wallet's own pages, and `useEditContactScreenLogic` uses it when the address or network changes, so a failed save keeps the contact under its old address.
- eb9f779: Give each explorer-backed operation one deadline, so a slow or trickling connection no longer holds the wallet for about 15 minutes. Every explorer read an operation makes shares its deadline, and the reads still running when it passes are aborted. A broadcast, with its fee bump check, its submissions and its lookups, has 120 seconds (`QBIT_BROADCAST_DEADLINE_MS`), counted from when it has the send guard's queue, so a send waiting behind another is still tried. A lookup the deadline cuts short leaves the outcome `unknown` and the inputs reserved. A pass with less than a submission's reply budget of the deadline left (`QBIT_BROADCAST_MIN_PASS_MS`, 15 seconds) sends nothing; a call that sent nothing reports `not_sent` only when no earlier call for the same transaction ended unknown, and `unknown` otherwise, with the inputs still reserved. Check status has 30 seconds (`QBIT_BROADCAST_STATUS_CHECK_DEADLINE_MS`) and the Speed up assessment 120 seconds (`QBIT_FEE_BUMP_ASSESSMENT_DEADLINE_MS`). A consolidation batch has 360 seconds (`QBIT_CONSOLIDATION_BATCH_DEADLINE_MS`) from when it has the account's scan: the large-read ceiling and a minute more, so every Prepare can finish at least one full page even at about 1 Mbit/s. A lifecycle lookup reads the whole transaction only to see that the explorer still has it, within 15 seconds (`QBIT_LIFECYCLE_TX_READ_DEADLINE_MS`); past that it is unknown. A history page or transaction read now has its 5-minute ceiling for all its attempts together, so an attempt cut off there while bytes were still arriving is not tried again.

A new `reset` option (`PersistentProxyOptions`) replaces the stored data with the template without reading it, and only the newest proxy for a key saves. The new `flushPersistentProxy` saves a proxy at once, in a single write, and rejects for a proxy that a newer one replaced; `PreferenceService.persist` uses it when the adapter has it. `PreferenceService.resetAllData` can therefore no longer be undone by a save the previous store still had pending or by a `persist` that runs while it resets.

  `ContactBookService` applies each change to a copy of the contact book and keeps it only once it is saved, one change at a time, so a failed write rejects and leaves the contacts as they are on disk. `resetAllData` now returns a promise. The wallet controller's `addContact`, `updateContact` and `removeContact` wait for the write. The extension's background storage now returns all data from `get()` without a key, accepts a write before the first read or after a failed one, keeps a write made while the first read is in flight, makes writes one at a time in call order so a read sees the writes requested before it, and stores and returns copies, so a caller changing an object it read or wrote no longer changes the cache.

- 4091176: Keep a Qbit send that spends the account's own unconfirmed change within qbit Core's ancestor size limit (#47). The node refuses a transaction whose in-mempool ancestors, itself included, total more than 404,000 vB (`DEFAULT_ANCESTOR_SIZE_LIMIT_KVB`), so a send that joined the change of a large unconfirmed send to many confirmed inputs was signed and then rejected as `too-long-mempool-chain`. `getQbitUtxos`, `getQbitUtxoSnapshot` and `getAddressUtxo` now list each change output's unconfirmed transactions with their sizes (`unconfirmedAncestors`, `QbitUnconfirmedAncestor`). - 4091176: Stop holding the inputs of a wallet send with an unknown broadcast outcome until the background restarts (#57). Such a send's claim stayed held after its recovery screen was left, because the popup or tab, and its UI port, usually stay open. A lifecycle probe that finds a wallet-owned claim's transaction pending now consumes that claim into recent spends while its recovery screen is still open, and one that finds it confirmed drops it. ### Major Changes

- 6f06a0b: Bind each approval to an id, so that a window settles only the approval it rendered (#311). `ApprovalService.requestApproval` now gives every approval a random 128-bit id, and `getApproval()` returns `{ id, data }` instead of the bare data (`undefined` when none is pending). `resolveApproval(id, data?, forceReject?)` and `rejectApproval(id, err?, stay?, isInternal?)` take that id first. They settle the approval only while it is still the pending one, checking and settling in one step, and return `true`; for any other id they settle nothing, close no window, emit no event and return `false`. Previously a window that rendered approval A resolved or rejected approval B when B replaced A between the window's read and its answer, for example after a lock or unlock, a window close or a dapp retry. `openNotification(winProps?, approvalId?)` opens the window for `approvalId`, by default the pending approval. `handleWindowRemoved` now rejects only the approval its window was opened for and returns whether it did, and a window that finishes opening after its approval settled is closed instead of becoming the approval window. An approval whose window fails to open is now rejected with `ErrorCodes.UNKNOWN` (`Approval window failed to open`), and one whose window is closed before it finishes opening with `UserCancel`, instead of staying pending and refusing every later request as already pending. `Approval['data']` is now `ApprovalData`: either a provider request (`ProviderApprovalData`, whose `state` and `approvalType` are optional because the provider omits them) or the provider's unlock request (`UnlockApprovalData`, `{ lock: true }`). These types and `PendingApproval` are exported from the package root.

  The wallet controller's `getApproval`, `resolveApproval` and `rejectApproval` change the same way, and `resolveUnlockApproval` still resolves only the unlock request, in one step. In `wallet-state`, `WalletController` and `ApprovalContextType` take the approval id as the first argument of `resolveApproval` and `rejectApproval`, which now resolve to whether they settled it, and `getApproval` returns the new `PendingApproval`. `ApprovalContextType` accepts `undefined` from a screen that rendered no approval, which settles nothing. `SignPsbtProps` and `SignMessageProps` take an optional `approvalId`, the approval their default handlers settle.

  Breaking change: callers must pass the id from `getApproval` to settle an approval. A call with any other value, including the old `(data, forceReject)` and `(reason, stay)` arguments, is ignored.

- 6f06a0b: Remove `clearKeyrings` from `walletController` and from the `WalletController` interface (#260). It emptied the live keyrings without locking the wallet, so the next vault write durably committed a vault without them. No UI called it; callers that need to drop the decrypted keyrings must call `lockWallet` instead.
- 6f06a0b: Stop an unlock from approving whatever request is pending (#267). `useUnlockCallback` used to call `resolveApproval()` after every password or TouchID unlock, which resolved any pending approval, so a Connect or SwitchChain request left open across an auto-lock was approved without the user. The wallet controller now exposes `resolveUnlockApproval()`, which resolves the pending approval only when the keyring is unlocked and that approval is the provider's unlock request (`{ lock: true }`). It checks and resolves in one step, so a second unlock can never approve the approval that follows, and it returns whether it resolved. `useUnlockCallback` calls it after unlocking, waits for the answer, ignores a failed call, and no longer uses the approval context or navigates; routing after the unlock is the caller's.

  Breaking change in `wallet-state`: `WalletContext` controller implementations must provide `resolveUnlockApproval(): Promise<boolean>`.

### Minor Changes

- 6f06a0b: Choose Qbit send inputs by value and keep every transaction within the standard size (#275, #276). Sends now rank outputs by effective value (the value less the fee the 3,762 vB input adds at the chosen rate), skip outputs that cannot pay for themselves, and take the largest first. A send no longer spends every small output the explorer listed before one that covers the amount, and no longer reports `Insufficient balance.` when one output could pay. No transaction carries more than the 106 single-key inputs that fit qbit Core's 400,000 WU `MAX_STANDARD_TX_WEIGHT` (with no witness discount, the finalized size). An amount only more inputs could reach fails before any signature budget is preflighted and names the largest amount one transaction can send. Send-all spends the 106 largest outputs and reports the others in the new `ToSignData.leftBehindInputCount` and `leftBehindSats`. `@qbit/wallet-shared` adds `QBIT_MAX_STANDARD_TX_WEIGHT`, `isQbitStandardTxSize`, `qbitP2mrMaxStandardInputCount`, `qbitP2mrInputFee`, `sortQbitCoinsByValue` and the selectors `selectQbitP2mrSendCoins` and `selectQbitP2mrSendAllCoins`, which both the controller and the wallet-state previews (`estimateQbitP2mrSendPreflight`, `estimateQbitP2mrSendAllPreflight`) use, so a preview matches the transaction that is built. Confirmed outputs are still spent before the account's own unconfirmed change, so an earlier payment keeps no descendant and stays eligible for a fee bump: `getQbitAddressUtxos` marks that change with the new optional `UTXO.unconfirmed` / `UnspentOutput.unconfirmed`, and the selector ranks it after the confirmed outputs, by value alone only when that order cannot build a standard transaction. The send preview now also reports `exceedsStandardSize`, `maxInputCount` and `maxStandardAmount`, and the send-all preview `leftBehindInputCount` and `leftBehindSats`; the send screen explains both cases.

  Recovery sweeps plan one transaction per batch of at most 106 inputs, all paying the source's destination account. The inputs fill the fewest batches, spread so the batches are even in value as well as in size, and the inputs of a batch too small to pay a dust output join a batch with room or form full batches of their own. Preparation drops an unsigned plan that exceeds the standard size and plans its inputs again. `advanceQbitRecoveryMigration` drops a signed plan whose transaction is gone and whose rebroadcast fails when the node rejects it as `tx-size` or its bytes exceed the standard size, since the same bytes can never be accepted, so the next preparation plans those inputs again instead of every pass failing. Other rejections, `dust` included, still fail the pass as before. `keyringService.preflightP2mrPsbtSigning` and `signP2mrPsbtWithCounter` refuse a PSBT whose signed size would exceed the standard limit before any signature counter is reserved.

  Show accounts whose outputs the explorer will not list (#277). When the explorer answers HTTP 500 for an address's output list while its statistics show more than 500 confirmed unspent outputs (the electrs `--utxos-limit` default), `getAddressBalanceV2` reports the statistics total as unavailable with the new `QbitBalanceSummary.utxoLimitExceeded` instead of failing, so the balance card no longer shows 0. The card labels that total, and the send screen says the wallet cannot choose inputs for such an account. The recovery review lists each account mapping once when a source is swept by several plans. A failed balance poll no longer leaves an unhandled rejection.

- 6f06a0b: Let accounts holding more outputs than the explorer lists spend, consolidate and migrate their funds (#277). When the explorer refuses an address's output list (HTTP 500 from `/address/:a/utxo` while its statistics show more than 500 confirmed unspent outputs), `getQbitUtxos`, `getQbitUtxoSnapshot`, `getAddressUtxo` and recovery preparation now read the outputs from the address's complete history instead, through the new `getQbitAddressUtxosClassifiedFromHistory` and `getQbitAddressUtxosClassifiedPastLimit`. The read fails closed: the statistics must match before and after the walk, the walk must hold their exact transaction counts, and the outputs it finds funded and spent must reconcile with their counts and sums. A history that moved or does not reconcile is read again a bounded number of times and otherwise fails. It never yields a smaller set. A history longer than `QBIT_UTXO_HISTORY_MAX_TRANSACTIONS` (10,000 transactions), or one the client's page ceiling cuts short, throws `QbitUtxoHistoryTooLargeError` before any partial result. The balance poll still reports the statistics total with `utxoLimitExceeded` and never walks history. Protected-asset lookups now run at most 16 at a time.

  The new `createQbitConsolidationPsbt` and `getQbitConsolidationStatus` let such an account sweep its outputs to its own address one batch at a time through the ordinary confirm, sign and broadcast flow. Each batch takes the largest mature confirmed outputs, at most 106, so it stays within the standard weight. It leaves out outputs worth no more than the fee their input adds, and reads on until the batch pays its fee and a dust output. Its inputs come from a newest-first walk of the history (`continueQbitAddressOutputScan`, new `getAddressHistoryPage` on both wallet clients) that resumes where the previous batch stopped, with a page budget per batch, so it also works for histories past the read limit. Every input is checked at `/tx/:txid/outspends` (`findQbitSpentOutpoints`) when the batch is built. It is checked again in `signPsbtV2` before any signature counter is reserved, including for a batch built here whose request has lost its details. A built batch's inputs stay out of later batches while a claim or recent spend holds them, and return once the explorer shows them unspent. Inputs a send claim, signing lock or recent broadcast holds stay out, so an interrupted run resumes without spending anything twice. `ToSignData.qbitConsolidation` (`QbitConsolidationBatch`) carries the batch's details. `@qbit/wallet-state` adds `useQbitConsolidationScreenLogic`, which publishes only the latest batch for the current account, network and fee rate. It also adds the `QbitConsolidationScreen` route. The send screen offers consolidation for an over-limit account (`showConsolidate`, `onClickConsolidate`) and shows Available as unknown (`--`) while the account's outputs cannot be read. The success screen after a batch offers the next one (`TxSuccessScreen.consolidation`, `onClickContinueConsolidation`).
