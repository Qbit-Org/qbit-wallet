Add the page side of Reset Wallet and the Settings → Security screen. The page-side `WalletController` type declares `resetWallet(password, options?)`; breaking change: it no longer declares `resetAllData`, which the wallet's pages could never call. `useResetWallet()` returns a callback that asks the background for the reset. `resetWalletState` is an action every slice handles: one dispatch returns the store to its first-run state (`isBooted` and `isUnlocked` false, no accounts, wallets, transactions or drafts), keeping `locale`, `themeMode` and `isReady`, so the persisted `ui` slice is saved empty. `RouteParamList` gains `SecurityScreen`, and `useSettingsTabScreenLogic` returns a `settings_security` row, placed before `settings_appearance`, that opens it. Breaking change: `useSettingsTabScreenLogic` no longer returns `settings_addressType`, as the Settings tab has no Address Type row. The entry is in Advanced Settings, and its logic is the new `useAddressTypeSettingLogic()` (with the type `AddressTypeSetting`), which returns `{ label, value, onClick }`: the address type by name, with the account's derivation path for a wallet that derives its accounts and can change type, and a tap that opens `AddressTypeScreen` or shows the tip for a wallet on a custom HD path. `useCreatePasswordScreenLogic` shows a `boot` rejection's message (or `unknown_error`) in its toast; it passed the rejection object itself before, which arrives from the background as a plain object and broke the screen. The page-side `WalletController` type declares `getWalletId()`, and the declarations of `unlock`, `changePassword` and `boot` name the reset errors they can reject with.
