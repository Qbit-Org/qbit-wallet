Give each wallet a color, and name new wallets "Wallet N" (#177). Every wallet the controller returns carries `color`, the palette key stored for it or else its slot's: `getKeyrings` (corrupted wallets included), `getCurrentKeyring`, `getEditingKeyring`, `setKeyringAlianName` and the wallets shown before they are added. A wallet gets its slot's color and its name when it is added, by `createKeyringWithMnemonics`, `restoreQbitKeyringWithFloors`, `createKeyringWithPublicKey`, `createKeyringWithAddress` or as the fresh wallet of `createQbitRecoveryMigrationWallet`. The name is the one the caller passed, which only `createKeyringWithPublicKey` takes and which it now uses when it is not blank, or else "Wallet N": N is the number of wallets once this one is added, removed wallets not counted, raised while another wallet is already named "Wallet N". Stored names are never rewritten, so a wallet named "Qbit HD Wallet #3" keeps that name. A wallet with no stored name, which only an earlier build can leave, gets "Wallet N" by its place when it is first read, instead of a name from its type and slot, and a corrupted wallet follows the same rule; a keyring of a type this build does not ship keeps its "Unsupported Wallet" label. A wallet without a stored color shows its slot's, and no color is written for it. `setKeyringColor(keyring, color)` stores the palette key the user picked and resolves with the wallet with its new color; it refuses any other value, and a wallet that is not in use, without storing anything. `setKeyringAlianName` refuses a wallet that is not in use the same way, and a name that is not a string or is blank, storing nothing, so a rename that reaches the background after the wallet was removed no longer stores its name again; a corrupted wallet can still be renamed. Both return a promise, where `setKeyringAlianName` returned the wallet at once, and they run one at a time in the order they are called, so a change that comes in later is never overwritten by an earlier one. Removing a wallet now forgets its name and color, and adding one replaces anything left under its key, so a new wallet never takes over another's. Two wallets added at once are each named, selected and shown by their own slot, where both used the last slot before, and a restore records its discovered receive indexes on the wallet it added. `deriveNewAccountFromMnemonic` names the account it derived before selecting it, so the name cannot go to an account selected elsewhere meanwhile. `WalletController` drops `getTotalKeyringCount`, and `UI_CONTROLLER_METHODS` drops it too: its only caller, the restore flow's suggested wallet name, is gone. `changeKeyring` selects from the wallet as it is when called rather than from the copy it is passed: it refuses a wallet removed since the caller read it, an account that wallet no longer holds at that place, and an account index that is not a whole number of zero or more, selecting and announcing nothing, and otherwise stores and announces the wallet's own copy of the account. `changeKeyring` also refuses, the same way, a page's copy of a wallet that is now listed only in another slot, as after the wallet was removed and its phrase restored again, where it switched to the wallet in the other slot. A wallet argument that is not an object with a list of accounts is refused as `Unknown wallet`, as `removeKeyring` refuses it, where it failed on a property read. `removeKeyring` removes a corrupted wallet, which it refused as no longer available because such a wallet lists no account to match it by: it takes the wallet still listed in the same slot under the same key and type, and still without accounts, reads that wallet's recovery record from its slot so that a migration it is part of still asks for confirmation, and refuses a wallet argument that is not an object with a list of accounts as `Unknown wallet`. After a removal `removeKeyring` returns the wallet then current: removing a wallet that is not current leaves the current wallet and account as they were, selecting and announcing nothing, where it used to switch to the last wallet's first account; removing the current wallet selects the last usable wallet with its first account, so when the last wallet is corrupted it no longer selects nothing and leaves the removed wallet's account stored as current. `removeKeyring` refuses a removal that would leave no usable wallet, with the `removing_the_last_wallet_is_not_allowed` message and before any recovery-risk check: corrupted wallets do not count, so the only usable wallet beside corrupted ones stays, a corrupted wallet goes while a usable one remains, and nothing is removed when no wallet is usable; the check runs in the queued removal, so two windows can no longer each remove one of the last two wallets, and again right before the wallet's slot is emptied, where no wallet can be added or removed meanwhile, so a wallet another window is adding no longer counts once its save fails: removing the only other usable wallet while that save is under way is refused instead of leaving no usable wallet. `removeKeyring` removes only the wallet in the slot the page listed it in, so a page's copy of a removed wallet whose phrase was restored again is refused instead of removing the restored wallet. It empties that slot only while the slot still holds the wallet the removal found there: when that wallet was being added and its save fails while the removal waits, and the next wallet added takes the slot it gives back, the removal is refused as no longer available, where it removed that next wallet and forgot its name and color. It reads the wallets afresh rather than through the keyring service's list of shown wallets, and it counts, keeps and selects only wallets whose slot still holds them, never the wallet it removed: wallets read before the removal, a lock or an addition no longer make the removed wallet current or let the last wallet be removed. The wallet stored as current stays whenever it is another wallet still in its slot and usable, whatever the wallets read list, so a wallet another window created or switched to meanwhile is no longer deselected, and `removeKeyring` returns that wallet as it is now. When a lock lands while the removal is saved it returns nothing and selects nothing, as when other windows keep adding wallets while it reads them. While a removal is under way, a `getCurrentKeyring` read that cannot use the wallet stored as current, as when the removal has emptied that wallet's slot, waits for the removal to settle and reads again, where it stored the first usable wallet's first account as current without announcing it: removing the current wallet while a site reads its account (`getCurrentAccount`, as provider `getAccounts` does) ends with the last usable wallet current and announced to connected sites and pages, and the site's read answers with that account, or with the wallet's own when the vault write fails. A `getCurrentKeyring` read during which another wallet was made current, or during which a removal under way when it began has settled, reads again and answers for the wallet current then, where it stored its own pick over the newer selection or answered with a wallet that had been replaced since. `getCurrentAccount` reads the wallets again, three reads at most, when the wallet as read does not hold the account stored as current, as when an account was derived, selected and announced while the wallets were read: it answered with the wallet's first account, so a site reading its account then got the first account's address after being told the new one. The first account still stands in, and is never stored, once three reads in a row miss the account stored as current. `changeAddressType` now runs after the wallet and chain changes already queued, such as a wallet removal, and changes the address type of the wallet it checked: when a removal reached the keyring service first, or was under way when it was called, the change was saved on the removed wallet's empty slot and reported as made, and the wallet current afterwards kept its address type. Once its change is saved, `changeAddressType` succeeds whatever is current then: it selects and announces the changed wallet's account, at the place of the account stored as current, only while that wallet is still current, so a switch another window made to another wallet while the change was saved stays and nothing more is announced, where it selected and announced the other wallet's account at the place of the account current before, or failed when that wallet had no account there; a lock while the change is saved no longer fails it either. An unlock now tells connected sites and pages the account it makes current when the wallet stored as current cannot be read and another wallet's first account is stored in its place, as after a lock that landed while the current wallet was removed, in this release or an earlier one; an unlock that keeps the account stored when the wallet locked announces nothing, as before. Switches the background makes itself, such as to a wallet or an account it has just added, are not refused that way: they select the wallet they built without reading the wallets again, and when a lock lands first, the addition still succeeds and nothing is selected or announced, where connected sites used to learn the new address while the wallet was locked.

`getMnemonics` answers only for a wallet with a recovery phrase that is still in use, checked after the password and again once the wallet is read: it refuses a wallet removed since the page read the wallets, or a wallet its slot does not hold, as no longer available, a malformed wallet argument as `Unknown wallet`, and a wallet without a phrase as `not_supported`, where it used to answer for whatever its slot held; a corrupted wallet still gets its phrase. For `getMnemonics`, `setKeyringAlianName` and `setKeyringColor` a wallet is in use while its slot still holds it: the wallet listed in the slot must hold the first account of the copy passed in, matched by public key or else by address, and for a corrupted wallet, which lists no account, the wallet listed in the slot must have the same key and type and list no account either. So a copy whose slot another wallet of its type has taken since, as the next wallet added does after an addition or a recovery migration's fresh wallet fails to save, or as new wallets do after a reset, is refused as no longer available, as is a copy read before the wallet's accounts were derived again by an address type change or a switch between mainnet and a test network; a wallet argument without a list of accounts is refused as `Unknown wallet`. `exportP2mrDescriptors`, which the export screen calls right after `getMnemonics` with the same copy, follows the same rule after the password: it refuses a malformed wallet argument as `Unknown wallet`, and a copy whose slot no longer holds that wallet, before or while the descriptors are read, as no longer available, where it exported the descriptors, private keys included, of whatever wallet the slot held; with no wallet argument it still exports the current wallet's, and a corrupted Qbit HD wallet still gets its descriptors.
