Recognize the explorer's refusal to list an over-limit address as it answers now (#169). Since v1.0.0, mempool-qbit answers `/address/:a/utxo` for such an address with HTTP 413 and electrs' reason, `Too many unspent transaction outputs (>N). Contact support to raise limits.`, where it used to answer a bare HTTP 500, so the wallet showed the raw error instead of reading the outputs from the address's history. A failed listing now counts as the limit when the explorer states it: electrs' reason at any status (qbit-electrs itself answers 400) or an HTTP 413, whatever the address's statistics show, since electrs refuses an address whose output set passed its limit at any point since it last cached that set, fewer outputs than the limit included. A bare 500 still counts, as before, only for an address whose statistics show more than the 500 confirmed unspent outputs the wallet assumes for such an older explorer (`QBIT_EXPLORER_DEFAULT_UTXO_LIMIT`). The new `qbitUtxoListRefusal` reads a listing failure as a refusal, stated or not, with the limit electrs' message states, and `isQbitUtxoListOverExplorerLimit` no longer reads the statistics for a stated one.

Consolidation asks the explorer instead of comparing the count with 500. `getQbitConsolidationStatus` and each `createQbitConsolidationPsbt` batch ask it for the account's outputs through the new `getQbitUtxoListLimit`: an account it lists is within the limit whatever its count, so preparing a batch for it fails with `consolidation_error_within_limit` (a listing reply that is not a list fails instead, as it does for a send), and one it refuses can consolidate with fewer outputs than the limit. The status reports `overLimit` with the limit the refusal states, the 500 assumed for a bare 500, or `null` when the refusal states none, and a batch's `qbitConsolidation.outputLimit` is the same limit.
