Send provider account events only to the origins they concern (#270). A change of the active chain no longer sends `accountsChanged []` to every connected origin. The new `sessionService.broadcastChainChange` still sends `chainChanged` and `networkChanged` to every connected origin, but sends `accountsChanged` only where the readable accounts changed: `[]` before the chain events to an origin whose grant matched the previous chain and not the new one, and the active address after them to an origin whose grant matches the new chain. Provider `switchChain` and `switchNetwork` now call the new `WalletController.switchProviderChain(origin, chain)`, which moves the requesting origin's grant inside the queued chain switch before anything is published. The requester therefore receives the new address and never `[]`. If the grant write fails, the committed switch is still announced and the request then rejects. A request for the chain that is already active no longer re-announces an unchanged account to every origin on that chain. The method is not on the UI allowlist. `WalletController.updateConnectSite` takes a `Partial<ConnectedSite>`. It no longer sends `networkChanged` to every origin: it read `data.origin`, which is undefined for a partial update. A settings update such as `allowQuickMultiSign` is written at once and sends nothing. An update to `chain` or `isConnected` queues behind chain switches and sends `accountsChanged` only to that origin, and only when its access to the active chain changed. When regtest access is lost and the keyring cannot be moved onto the mainnet path, the mainnet switch is announced with no account. An update that sets `isConnected: false` sends `accountsChanged []` and the `disconnect` event, as `removeConnectedSite` does, whichever chain the grant was on. Announced accounts are read with `getCurrentAccount()`, the lookup the provider's `getAccounts()` uses. A failed read announces no account and does not fail the chain switch. Locking still emits no `accountsChanged`.

In `@qbit/wallet-connect-react`, `WalletProvider` no longer calls `wallet.disconnect()`, which revokes the grant in the wallet, from event handlers. An empty `accountsChanged`, or a refresh that finds no usable account, now clears only the account and keeps the listeners, so while the page stays open the account comes back when the wallet sends it again. A refresh that fails keeps the current state, as before. The `disconnect` event, and a network change with `disconnectOnNetworkChange`, clear the page's connection state without revoking; events that still reach the listeners of a cleared connection are ignored. A newer event or a cleared connection now discards an account refresh still in flight, and `isConnecting` stays true until the last overlapping refresh settles. The context's `disconnect()` still revokes.
