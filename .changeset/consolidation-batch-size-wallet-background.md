Let the user choose a consolidation batch's size, and read the explorer's refusal of a transaction as too large as "not sent" (#170). `createQbitConsolidationPsbt(request)` takes `maxInputs`, a whole number from 2 to the account's `maxInputCount`; omitted, it is that maximum. Any other value, `null` included (the UI port carries NaN and ±Infinity as `null`), is refused with a `RangeError` before any explorer read, and a request that is not an object with a `TypeError`. The request's `feeRate` likewise: only an omitted rate means the normal rate, and `null` is refused with the other rates outside the wallet's policy, before any explorer read, where it used to mean the normal rate. The batch takes at most that many inputs, its history walk stops once it holds that many, and it records the size as `qbitConsolidation.maxInputs`; inputs earlier batches handed out are still checked again up to twice the account's maximum. `getQbitConsolidationStatus` also returns `batchShape`, so the screen can price a batch of any size. Batches, send-all, sends and recovery plans keep to qbit Core's standard size, 106 single-key inputs, and rely on the explorer measuring the same size, as it does from explorer 1.1.0 (qbit-explorer#58). A broadcast refused at HTTP 400 with a code-only -3, the explorer's answer for a transaction over its limit, is classified `too_large` and definitive: it reads `not_sent` once the follow-up lookups find the transaction absent, which frees its inputs, `unknown` while they cannot run, and success when they find it. It used to read "Payment status unknown" and hold the inputs for 10 minutes to 24 hours. A -3 that carries a message, and any reply mentioning "already", is read as before, and a failed explorer read before a broadcast that answers that way is reported as a server error. `isQbitTxSizeBroadcastRejection` does not recognize the refusal: the limit is a deployment setting, not a verdict on the bytes. An explorer before 1.1.0 weighed base bytes ×4 plus witness bytes and so refuses 103 to 106 single-key inputs that way: a consolidation batch, send or send-all of that size reads "not sent" and frees its inputs, and a batch of 102 or fewer goes through, while a recovery plan stays signed and the pass that sends it ends with that refusal, so the migration waits there until the explorer is updated and a later pass sends it again.
