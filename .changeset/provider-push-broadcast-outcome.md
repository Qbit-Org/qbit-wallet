Reconcile an ambiguous provider `pushTx` or `pushPsbt` broadcast instead of reporting the endpoint's raw error (#268). Both now broadcast through the new `WalletController.broadcastQbitProviderTx`, which reaches the send path's verdicts (`broadcastQbitTx`) and never throws. A 2xx answer must echo the txid computed from the bytes, which is what the dapp now receives in place of the endpoint's answer. A failure after dispatch is looked up by txid, and a transaction the lookup finds is reported as sent. A definitive node rejection with absence proven, and every refusal before dispatch, still reject with a plain error, now carrying the sanitized reason instead of the endpoint's URL and body. Anything else (a timeout, a network or gateway error, a 2xx without the txid, a lookup that cannot settle it) rejects with `ErrorCodes.QBIT_BROADCAST_OUTCOME_UNKNOWN` (`-32010`) and `data: { outcome: 'unknown', chain, txid }`, as a provider `sendQbit` already does, so a dapp can look the transaction up instead of retrying into a second payment. An unknown outcome keeps the transaction's inputs reserved as recently spent only when the user approved signing that transaction for a dapp: provider `signPsbt` and `signPsbts` now record the transactions they return (`WalletController.recordQbitProviderSignings`, `qbitSendGuardService.recordProviderSigning`, memory only and bounded by `QBIT_PROVIDER_SIGNING_LIMIT`, 256), and `qbitSendGuardService.recordInconclusiveProviderPush` reserves the inputs of only those. A push needs no approval, so any other push still reserves nothing unless it is accepted or found. A dapp's push proven not sent forgets no reservation, since a txid does not cover the witness. `walletController.pushTx` keeps its behaviour for the recovery migration.
