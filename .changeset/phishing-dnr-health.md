Retry a failed phishing block rule install and report its health (#349). Before, when `updateDynamicRules` failed at service-worker start, the error was only logged: the denylist had no network layer until the next start, and an upgraded profile kept the inert redirect rules of 1.0.4. `PhishingController` now retries the install after 1, 4 and 15 seconds, then every minute while the service worker runs, up to ten attempts. After each failure it removes every dynamic rule but a block rule on its own, so those redirect rules cannot linger, and keeps a block rule an earlier install left. A successful install counts only once the browser reads the rule back with every domain, and a worker start that finds that rule already in place, alone, leaves it as it is. `GET_PHISHING_STATS` also answers `networkRules`, the rule's health: `installing`, `installed`, `retrying`, `failed`, `unknown` or `unsupported`, with the attempts, the last error, the next retry, the number of domains the browser holds and the denylist entries left out. An `installed` state is checked against the browser's rules at each read, so it is never a stale one, and a rule found missing reads as `retrying` and is installed again. An install that a newer one supersedes answers with the newer one's outcome. `GET_PHISHING_STATS` is now answered only for the wallet's own pages, like the other messages that lift or reload protection. `FORCE_UPDATE_PHISHING_LIST` now also installs the rule again through `forceUpdate()`, which rejects, and so the message answers `{ error }`, when the rule is not installed after its first attempt.

In `@qbit/phishing-detect`, `parseDnrDomain()` and `partitionDnrDomains()` are new. They return the form a DNR rule's `requestDomains` takes, or why an entry cannot go in one (`not-a-string`, `empty`, `non-ascii` or `not-a-public-hostname`), so the extension leaves out and logs a bad entry rather than letting it fail the whole rule.

`@qbit/wallet-shared` exports the health type as `PhishingNetworkRuleHealth`.

The extension's content script now stops a top-frame page whose host the bundled denylist covers before the page's own script runs, until the background answers. A page sent to the warning page stays stopped, and one whose check does not complete shows a notice with a retry. A page the user proceeded to is recorded in its sessionStorage and reloaded once. A page whose sessionStorage cannot be used, such as a sandboxed one or one whose site data is blocked, stays held, and a page held again on a reload is not reloaded once more without the user asking.
