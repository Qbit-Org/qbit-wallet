Show the balance split of an account over the explorer's UTXO limit once the wallet has read its outputs, and show Unavailable as unknown on the send screen while that split is unknown.

`getAddressBalanceV2` now takes the split of an over-limit address from the latest output read from its history on that network (`getQbitUtxoSnapshot`, which the send screen runs), and only while the address statistics read as they did when that read's walk verified them: any new transaction for the address changes them. A coinbase output matures with no such change, and turns immature again when the chain rolls back, so a read that left an immature one out counts only until the tip reaches the height where it matures, and a read that took one in only while the tip stays at or above the height where every such output is mature; the balance read looks up the tip only for a read with coinbase outputs. Available is what a send may select from that read, less the outputs the send guard reserves, bounded as on the listing path: the confirmed outputs never count for more than the confirmed balance, and the whole never for more than the total. Unavailable is the rest of the total, and `immatureBalance` and `pendingBalance` stay `null`. Without such a read, or when the reservations cannot be read within the balance read's bounded wait for the send guard, the split stays unknown (`availableBalance: null`); an over-limit address keeps `utxoLimitExceeded` either way. The wallet keeps only the latest read per address and network, for the four addresses most recently used on each network, in memory, from a read that completed, and only what the split needs of each output; a read that started later replaces one that started earlier, even when it found less history, as after an eviction. Nothing is kept while the wallet is locked, and locking it or removing a keyring forgets every kept read, including that of a read still running; a lock forgets them before it waits, so they are gone while a slow lock waits and after one that fails. The split uses the statistics the balance read's limit check fetched, without reading them again. For this `getQbitSpendableBalanceV2` takes an optional `readOutputs(stats)`, `readQbitAddressUtxos` returns the outputs with the statistics the walk verified (`QbitClassifiedUtxos.historyStats`), `qbitReadOutput` keeps what the split needs of an output, and `QbitLatestAnswers` keeps the latest answer per scope and slot. The `QbitBalanceSummary.utxoLimitExceeded` documentation describes the split.

`useBalanceCardLogic` shows that split as the background reports it. `useTxCreateScreenLogic` now returns `--` for `unavailableAmount` whenever it shows Available as `--`, with `showUnavailable` true, instead of showing the whole balance as unavailable.

`createSendQbitPsbt` and `createSendAllQbitPsbt` require `qbitUtxoAddress` with `qbitUtxos`, the account the outputs were read for, and refuse the request when it is missing or not the selected account; `usePrepareSendQBTCallback` always passes it, with the network, as recorded for the cached read. Both builders also refuse an output without a scriptPubKey, or with one other than the selected account's, instead of taking it for the account's own or leaving it out; the send-all builder no longer stamps the account's scriptPubKey on an output without one, and the recovery migration's sweep refuses such an output too, while its read-only status checks count one as still needing migration instead of failing. One rule decides it everywhere: `isQbitAccountOutput` in `@qbit/wallet-shared` takes an output as the account's only when it carries a non-empty scriptPubKey equal to the account's. The balance paths, both builders and the send screen (`getQbitP2mrSpendableUtxos`) use it, so Available and the send screen's preflight never include an output a builder refuses.

In `@qbit/wallet-state`, `WalletController.createSendQbitPsbt` and `WalletController.createSendAllQbitPsbt` now require `qbitUtxoAddress`.
