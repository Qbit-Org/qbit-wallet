Read the whole history of a mempool-qbit address whose pending transactions fill whole pages. qbit-electrs answers the cursor of the last pending row with an empty page instead of the confirmed rows after it, and `@qbit-oss/api`'s reads of the combined route took that page for the end, so with 50, 100 or any other multiple of 50 pending transactions they rejected with `invalid_cursor` while the address had confirmed history. The over-limit output read behind the send screen and recovery (`getQbitAddressUtxosClassifiedFromHistory`), the restore floor scan (`observeQbitPqcSignatureActivity`), recovery's spender check (`observeQbitPqcSpentOutpoints`), activity history (`getQbitAccountHistory`) and its revision probe (`probeQbitAccountHistoryRevision`) failed with them, so a restored wallet with confirmed history stayed sign-locked. `QbitWalletMempoolClient` now overrides `getAddressHistory` and `getAddressTxs` with reads that step back over that page, as consolidation already did, so every caller reads past it. The page walk is shared with `continueQbitAddressOutputScan`, which reads as before; `QbitAddressOutputScan` now extends the new `QbitHistoryWalkCursor`, with the same fields. Both reads otherwise keep the library's contract: one operation scope (the client's signal, and the caller's signal and deadline) covers each call; `getAddressHistory` checks each row (well formed, touching the address, listed once), reads the address statistics before and after, walks once more if they moved, returns only a history that holds exactly their counts, and keeps to `maxPages` (at most the client's `maxAddressHistoryPages`, now also `maxHistoryWalkPages`) and `maxTransactions` across both walks; `getAddressTxs` returns at most 25 confirmed rows, skips a row a later page repeats, and stops at a short page. Each caller still requires the history to match the statistics it read around it, so no floor is ever taken from part of a history. If the pending rows change between the empty page and the one after the step back, the read fails with `invalid_cursor` and is retried, as before.

`prepareQbitRecoveryMigration` no longer fails the whole pass for a source whose history read still cannot be shown complete once its retries are spent (`invalid_cursor`, or a history that kept moving). It plans the other sources and returns that source in `deferredSources` with the new reason `history_incomplete`, which the migration screen names. Its funds keep the migration open, and `advanceQbitRecoveryMigration` does not archive past it. The check of an already archived migration does not count such a read as new funds: it fails as before and reopens nothing, while a history too long to read still reopens it. Every other read failure still fails the pass. `QbitRecoveryDeferredSource` is now a union of the two reasons, and only `history_too_large` carries `maxTransactions`. Deferred sources are returned to the UI and never stored. `isQbitSnapshotUnstableError` is now exported.
