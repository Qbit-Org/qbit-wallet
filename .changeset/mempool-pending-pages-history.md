Read the whole history of a mempool-qbit address whose pending transactions fill whole pages. qbit-electrs answers the cursor of the last pending row with an empty page instead of the confirmed rows after it, and `@qbit-oss/api`'s history walk took that page for the end, so with 50, 100 or any other multiple of 50 pending transactions it rejected with `invalid_cursor` while the address had confirmed history. The over-limit output read behind the send screen and recovery (`getQbitAddressUtxosClassifiedFromHistory`), the restore floor scan (`observeQbitPqcSignatureActivity`), recovery's spender check (`observeQbitPqcSpentOutpoints`) and activity history (`getQbitAccountHistory`) failed with it, so a restored wallet with confirmed history stayed sign-locked. On `QbitWalletMempoolClient` these reads now walk the combined route themselves and step back over that page, as consolidation already did. The page walk is shared with `continueQbitAddressOutputScan`, which reads as before; `QbitAddressOutputScan` now extends the new `QbitHistoryWalkCursor`, with the same fields. The walk checks each row as the library's does (well formed, touching the address, listed once) and keeps to the same page and transaction budgets, within the client's `maxAddressHistoryPages`, now also `maxHistoryWalkPages`. Each caller still requires the walk to hold exactly the counts in the address statistics read around it, so no floor is ever taken from part of a history. If the pending rows change between the empty page and the one after the step back, the read fails with `invalid_cursor` and is retried, as before. Esplora surfaces keep the library's walk.

`prepareQbitRecoveryMigration` no longer fails the whole pass for a source whose history read still cannot be shown complete once its retries are spent (`invalid_cursor`, or a history that kept moving). It plans the other sources and returns that source in `deferredSources` with the new reason `history_incomplete`, which the migration screen names. Its funds keep the migration open, and `advanceQbitRecoveryMigration` neither archives past it nor fails on it, as for a history too long to read. Every other read failure still fails the pass. `QbitRecoveryDeferredSource` is now a union of the two reasons, and only `history_too_large` carries `maxTransactions`. Deferred sources are returned to the UI and never stored. `isQbitSnapshotUnstableError` is now exported.
