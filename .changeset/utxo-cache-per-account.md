Keep the send screen's cached outputs with the account they were read for (#342). For an account over the explorer's output limit the read walks the address history, which can take minutes. A walk that landed after the user had switched accounts replaced the new account's cached outputs, so its send screen showed 0 available and Next failed with `Amount exceeds your available balance` or `Insufficient balance.` until the screen was opened again. `QbitUtxoSnapshot` now names the `address` it was read for, and the transactions slice keeps it as `utxosAddress`, with the read that loaded the outputs as `utxosRead`. `useFetchUtxosCallback` caches an answer only when its caller has not aborted it (the new optional `signal`), its account and network are still the selected ones, and the cache does not already hold a later read's answer for them. It rejects an answer for any account or network other than the ones it asked for. `useUtxos` now returns the cached outputs only for the selected account on the active network, and the new `useUtxosLoaded` says whether the cache holds them; `useUtxosChain` still reports the cache's network whichever account it holds. Preparing a send reloads a cache that holds another account's outputs instead of spending from it. The send screen reads again, without covering the screen, when its account or network changes, and abandons its read when it closes. `getQbitUtxoSnapshot` joins a read already running for the same account through the same API client, while the address statistics read the same as when it started, instead of starting another history walk, and applies the send reservations to each answer after the read. `getQbitUtxos` always reads afresh.
