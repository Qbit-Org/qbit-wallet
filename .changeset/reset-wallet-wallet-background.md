Add `WalletController.resetWallet(password, options?)`, the reset a wallet page may ask for. It runs as one change on the chain-state queue and erases nothing unless the wallet is unlocked, `password` is the wallet's (checked in the background) and the recovery risks of every wallet were acknowledged in `options` as `removeKeyring`'s are (`QBIT_RECOVERY_REMOVAL_ACK_REQUIRED` with the reasons of all wallets in `data.reasons` otherwise). It then stops local signings, locks the wallet without announcing it, waits for vault writes under way, and erases the wallets and the password, the biometric unlock record, every site's grant, the contacts, the send records, the phishing bypasses, the local regtest consent, the pending approval and the controller's caches, and returns every preference to its default except the language and the theme. Each site that was connected receives `accountsChanged []` and `disconnect`, and every wallet page receives `BUS_METHODS.WALLET_RESET` once. A reset that erased the keys but could not clear the rest rejects with `WALLET_RESET_INCOMPLETE` and stays pending: the next `resetWallet`, the next start of the background (`finishPendingWalletReset()`, not callable from a page) or the next `boot` finishes it, so a new wallet inherits no names, colors, grants or contacts. `boot` now runs on the chain-state queue and refuses with `WALLET_RESET_INCOMPLETE` while a pending reset cannot be finished. With `options.lastWalletKey`, the reset a page offered as the removal of its last usable wallet, it checks again on the live wallets that the named wallet is still the last usable one, as a removal judges its own refusal, and rejects with `WALLET_RESET_NOT_LAST_WALLET`, changing nothing, otherwise, judging again right before it locks. Every reset that is going to erase first waits for wallet additions a page already has under way, and so does `boot`, so none can resume into the next vault. The keyring erase is tried up to three times; if it keeps failing, or the vault is still loaded afterwards, the reset rejects with `WALLET_RESET_OUTCOME_UNKNOWN`, leaves the wallet locked and keeps the reset pending, and the start-up completion, which now tells the sites that still hold grants and every wallet page, finishes it if storage holds no keys. Every completion run also finishes the keyring's own erase, only while nothing is booted and no vault is kept, so the keyring's public key cache never outlives the wallets. Breaking change: `runForUiPort` takes the method name as a required third argument. It holds a wallet page's call made while a reset runs: it is refused if that reset erased the wallets, refused with `WALLET_RESET_OUTCOME_UNKNOWN` if the reset's outcome is unknown, and run otherwise, unless its page closed while it waited; only `resetWallet` itself is not held. A reset that fails before the keys begin to be erased takes back its pending mark, if it set it itself. After `WALLET_RESET_OUTCOME_UNKNOWN`, `unlock` (by any route), `changePassword`, `boot` and a further `resetWallet` are refused with that code until the background starts again, so that storage alone decides whether the wallets were erased. At its start the background forgets a pending mark it finds beside a wallet, erasing nothing. `walletResetGeneration` moves when a reset begins to erase the keys, and a website request whose context was captured before it is refused, so an approval given just before a reset grants nothing afterwards. A read that began before a reset writes nothing of the erased wallets afterwards (a late balance, history page or snapshot, or fallback current wallet), and the history read fails; a website's `getBalance` is covered through the new `getAddressBalanceSince(address, generation)`, which is not callable from a page. The completion of a pending reset holds wallet pages' calls as a reset does, at the background's start and inside `boot` as well, and refuses them once it ends. `getWalletId()`, callable from a page, returns an opaque random id of the wallet set up in this browser: null while nothing is booted, created on first read, unchanged by locks, password changes, additions, removals and restarts, and different after a reset. `getAllAddresses` refuses a page's copy of a wallet without a phrase that is no longer the one in its slot, as rename and color already do (a phrase wallet is read by slot, since nothing is taken from the page's copy), and `setAccountAlianName` refuses an account its wallet no longer lists, returns a promise, and runs in order with wallet renames and color changes. `runForUiPort` takes an optional fourth argument, the id of the wallet the page shows, and refuses a request naming a wallet that is not the one set up now with `WALLET_PAGE_OUT_OF_DATE`, before the call runs and whatever the method; it judges nothing before the keyring and the preferences have loaded, and lets `resetWallet` through while nothing is booted, so that the page of an erased wallet can still finish its clearing; A change a wallet page queues on the chain-state or the wallet-label queue is judged again when its job starts, `resetWallet` included, and refused with `WALLET_PAGE_OUT_OF_DATE` if the wallet it named is no longer the one set up. `RegtestAccessService.acknowledge()` refuses an acknowledgement that a reset or a permission removal overtook. The phishing controller gains `clearSessionBypasses()`. A reset that goes ahead to erase halts the send plans before it locks, waiting for plan work under way, so nothing of a plan is signed, broadcast, written or held from then on; it erases every stored plan in a step of its own, counted for `WALLET_RESET_INCOMPLETE` like the others, and lets plans go on only once every step succeeded, so after a reset that began to erase the keys and could not finish they stay halted until a completion clears everything. A reset that erases nothing lets them go on. `resetAllData` stays refused by the UI port, and the last usable wallet still cannot be removed with `removeKeyring`.
