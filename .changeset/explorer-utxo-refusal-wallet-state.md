`useQbitConsolidationScreenLogic` takes whether the account is over the explorer's listing limit from the status's `overLimit`, the explorer's own answer, instead of comparing its count with the limit, and no longer estimates the batches left, at the account's maximum or at a chosen batch size (#169): electrs keeps refusing an address that once held more outputs than its limit, so consolidating does not make the explorer list it again; only the operator raising the limit does. The status line names the limit only when the explorer's refusal states one (`consolidation_status`, or `consolidation_status_no_limit`), whatever the batch size, the new `refusalText` (`consolidation_refusal_lasts`) says, when the refusal names a limit or the wallet assumes 500 for a bare HTTP 500, that it lasts until the operator raises that limit, and `consolidation_within_limit` takes no limit. `useTxCreateScreenLogic` returns the send screen's consolidation note as `consolidationNote`, empty once the account's outputs could not be read from its history either, since the note says that sends read them from there. The extension shows the refusal line on the consolidation screen and drops `consolidation_status_confirming` and `consolidation_status_counts`. In all six locales, the send screen no longer says that consolidating lets the account send and migrate normally again, and says that reopening Send tries a failed history read again (`consolidation_send_note`, `utxo_limit_exceeded_send`); the recovery screen no longer asks the user to consolidate a deferred account until the explorer lists it (`qbit_recovery_deferred_history_too_large`); and neither the balance card nor the recovery screen blames too many outputs for a refusal that can outlast them (`utxo_limit_exceeded_balance`, `qbit_recovery_deferred_history_incomplete`).
