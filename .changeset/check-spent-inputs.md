Opening Send no longer reads the transaction behind every output: outputs at least 1,000 blocks deep come from the explorer's listing, and each input a transaction actually spends is read and checked (its transaction, output, value, script and coinbase maturity) right before it is built and again before it is signed; a send plan checks every input its steps spend in one pass before its first signature, and each step's inputs again before that step is signed. This covers sends, sends of everything, consolidation batches, recovery sweeps and every step of a send plan (#210). An input that fails its check stops the transaction with a message naming why; nothing is signed and nothing else is chosen in its place.

- `readQbitAddressUtxos` and `readQbitAddressUtxosRidingOut`, the reads behind the send screen's snapshot, both send builders and a send plan's revision (`qbitSendInputsOn`), list candidates: a confirmed output at least 1,000 blocks deep is classified from the listing alone, as the balance read classifies it (spendable and mature, with the listed value and the address's script, its depth judged from the listing's newest block and then from the tip asked for with the listing). Kept facts are served to these reads exactly as before, they have no `maxOutpoints` cap, and an address with no derivable script is read output by output as before. `getQbitAddressUtxos`, `getQbitAddressUtxosClassified`, `getQbitAddressUtxosClassifiedPastLimit` (the recovery passes) and `getQbitAddressUtxosClassifiedFromHistory` still read and check every output.
- `checkQbitSpendInputs(client, address, inputs, options)` reads the funding transaction of each input, one lookup per distinct transaction through the shared reader's limiter at the rates of any classification, and checks that it has the input's txid and, at the input's index, an output of exactly the value signed and the account's P2MR script. A coinbase output must be confirmed and mature by a tip read for this check, and an unconfirmed output must be the account's own change all the way down, whose unconfirmed ancestors it reads. A kept fact never serves it; what it reads is kept as any classification keeps it. Every read runs under one signal, the caller's and its deadline, `QBIT_SPEND_CHECK_DEADLINE_MS` (60 s) unless the caller gives one, and nothing it started is left running when it settles, even when it cannot begin. It rejects with `QbitSpendInputCheckError`, whose `problem` is `mismatch` (another txid, no output at the index, another value or another script, or an input that is no output at all: a malformed txid, index or value, or an output spent twice, refused before any read), `not_spendable` (an immature or unconfirmed coinbase, an unconfirmed output that is not own change, or own change with as many unconfirmed transactions before it as qbit Core allows), `not_found` (the explorer has no such transaction) or `unchecked` (anything that could not be read, the deadline included, an ancestry the walk cannot follow, or a tip below the coinbase's block; never reported as a mismatch). The controller's error carries the `send_input_check_*` message of the cause in the user's language; across the UI port a page receives that message (`problem` stays in the background). An input of a transaction the caller holds (`ownTransactions`: a plan's own merges) is checked against it with no lookup. With `rideOutServerErrors`, the lookups, the tip and the reads of ancestors ride out the explorer's server errors.
- Both builders check the inputs they selected before they build: `createSendQbitPsbt`, and `createSendAllQbitPsbtForAccount` for sends of everything, consolidation batches and the recovery migration. A PSBT's inputs come only from that check. A consolidation batch's check runs within the batch's deadline (`QBIT_CONSOLIDATION_BATCH_DEADLINE_MS`). Every local signing checks the inputs of the bytes it signs again (`signQbitP2mrLocally`), before the keyring takes a signature counter unit, and refuses if the page closed, the wallet locked, or the network or the selected account changed meanwhile; a recovery migration's plan is validated again. A signing asked while the wallet reads locked is checked as any other (the memory store can read locked while the keyrings are live: during an unlock, and while a lock waits for the keyring's mutex) and reaches the keyring only checked. One asked while a lock still waits for that mutex is checked, where it was signed unchecked before, and whether the keyrings are live is decided when the keyring is called, after the send guard's queue, not when the check ends: if the lock drops them before that call, the keyring refuses it, unless the wallet is unlocked again first, when it is signed, checked. One asked once the keyrings are dropped is refused by the keyring, as before, but now after the check's reads, and is signed, checked, if the wallet is unlocked meanwhile; one whose check fails is refused with the check's cause, where the keyring's own error came before. A fee bump spends exactly the outputs of the transaction it replaces, and its eligibility (`getQbitFeeBumpEligibility`, and the assessment every build of one runs) checks them as the wallet's signing will, so a bump offered passed, when its eligibility was assessed, the check its signing makes. `inputs_not_spendable` (a new `QbitFeeBumpUnavailableReason`) is reported when an input is an unconfirmed output whose transaction, or an unconfirmed one before it, spends an output that is not the account's: someone else's unconfirmed payment to the account, or change from an unconfirmed transaction that also spent someone else's output. Only an original signed without that check spends one: through a website's request, or by other software holding the same key. Change with too many unconfirmed transactions before it, and an immature coinbase output, are refused the same way, but an original the mempool accepted spends one only while the explorer lags or after a reorganisation. `unverifiable` is reported when an input's funding transaction disagrees with it or is missing, and when the check cannot be completed (a read that fails or runs out of time), which the build reports as the bump being unavailable, as for any other read of the assessment. That check runs last, only for a bump otherwise eligible, with a deadline of its own after the assessment's reads of the original: the signing's 60 s (`QBIT_SPEND_CHECK_DEADLINE_MS`), so the whole assessment ends within 180 s. It reads the tip once, at once and outside the limiter, the funding transaction of each input, and, for an unconfirmed one, every parent of each unconfirmed transaction before it, confirmed parents included, each transaction once and through the limiter. The eligibility, the build and the signing each run it, with no polling: once each time a pending transaction's detail opens, once per build, and once more when the wallet signs. A bump the wallet signs is checked again then; an External signer's bump, signed elsewhere, is checked at eligibility and at build only. External signers spend their units outside the wallet, so for them the check when building is the only one.
- A send plan checks every input its steps spend that is not an output of its own merges in one pass before its first signature, and the inputs a revision or a restart brings in before the next, so an input that fails stops the plan before anything of it is signed; then each step's inputs before that step is signed, ahead of its overlap check, signature batch and keyring, riding out server errors (`QbitSendPlanEngineHost.checkSpendInputs`, a new required host method, given the plan's own merges by txid). Its deadline grows by `QBIT_SPEND_CHECK_MS_PER_LOOKUP` (20 ms) per funding transaction looked up (`qbitSpendCheckDeadlineMs`). A step that could not go on (a lock, a cancel, another network) reads nothing. A plan whose input fails pauses with the cause: `input_check_mismatch`, `input_check_not_spendable`, `input_check_not_found` or `input_check_unchecked`, each offering Continue, which checks again; `input_check_not_found` and `input_check_not_spendable` also offer a replan, which reads the outputs as they are now and checks what it selects before it signs. A void merge, which is never signed, is left out of the one pass. An input that passed the pass and then failed its step's own check is read again by the next pass, so a continue or a replan that spends it again stops before signing anything more.
- Provider signing alone skips the check when signed, for two declared kinds of bytes: a website's PSBT, only the exact bytes of an entry its request admitted as its approval opened (`admitQbitWebsitePsbts`), signed with that website's provider context, for as long as that approval is open, across a lock or a wallet's removal as well, until it settles or a reset clears every admission; and a provider send, only the exact bytes the wallet built and checked for an open provider request, under the claim the background minted from them (`createQbitSendBroadcastClaim`, recorded by `openQbitProviderSendRequest` until `settleQbitProviderSendRequest`). Either kind must still hold as the keyring is called, for the bytes as they are then: a signing whose approval or request settled after it was let skip the check (during a consolidation's re-check of its inputs, say, or its wait in the send guard's queue) is refused there, unsigned. Other bytes under such a claim are checked; a claim that is present but not a well-formed claim (`null`, `false`, `0` and `''` included) refuses the signing before anything is read, a consolidation's re-check of its inputs included.
- The protected-asset guard of a recovery migration checks the listed values it counts against their funding transactions before an ordinary input may ride along.
- Nothing is chosen in place of an input that fails: the build or the signing stops with the message of its cause, which says what happened and that the wallet stopped before signing; only a check that could not be made adds "Try again in a moment.", true wherever it shows, as a retry reads again, and the other causes offer no remedy, as none is.
- Opening Send on an address with 20,000 outputs 1,000 or more blocks deep, 5 younger ones and 2 unconfirmed change outputs made 20,008 transaction lookups and now makes 8. A check makes one lookup per distinct funding transaction, at most 106 for a transaction of 106 inputs, plus the unconfirmed ancestors of any unconfirmed input, and one tip read.
