Keep a Qbit send that spends the account's own unconfirmed change within qbit Core's ancestor size limit (#345). The node refuses a transaction whose in-mempool ancestors, itself included, total more than 404,000 vB (`DEFAULT_ANCESTOR_SIZE_LIMIT_KVB`), so a send that joined the change of a large unconfirmed send to many confirmed inputs was signed and then rejected as `too-long-mempool-chain`. `getQbitUtxos`, `getQbitUtxoSnapshot` and `getAddressUtxo` now list each change output's unconfirmed transactions with their sizes (`unconfirmedAncestors`, `QbitUnconfirmedAncestor`). Change whose transactions the explorer does not size is left out, like change of unreadable ancestry. `selectQbitP2mrSendCoins` keeps every selection that holds change within the new `QBIT_MEMPOOL_ANCESTOR_SIZE_LIMIT` together with those transactions, counting a shared one once and passing over change that would cross it. It reports a send that only this limit stops as `exceeds_ancestor_size`, and `selectQbitP2mrSendAllCoins` reports `exceedsAncestorSize`. `createSendQbitPsbt` and `createSendAllQbitPsbt` refuse such a send before signing with `send_exceeds_ancestor_size`. The send screen's preflight (`exceedsAncestorSize`) shows the same message: wait for the earlier send to confirm, or send a smaller amount. Fee bumps keep the original's inputs and never grow it, so they stay within the package the node already accepted.
