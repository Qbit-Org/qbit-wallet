'@qbit/wallet-background': patch

Send the same signed bytes again when a broadcast's outcome is unknown and a lookup by txid finds the transaction absent (#356). `@qbit-oss/api`'s `broadcastTx` never re-sends a submission that may have reached the node, so since 1.0.5 a transient 502, a timeout after sending or a reply that was not the txid ended as "unknown" and needed reconciliation. `WalletController.broadcastQbitTx`, which wallet sends and the provider's `sendQbit` use, and `broadcastQbitProviderTx`, which the provider's `pushTx` and `pushPsbt` use, now re-send exactly the same bytes up to twice, after 1 and 3 seconds, and start no re-send more than 30 seconds after the first dispatch. Each re-send follows a lookup that found the transaction absent and passes the send guard again: it goes out only while the claim for exactly that transaction is still held, or, for a website's push, which has no claim, while no claim, external signing lock or other broadcast has taken its inputs. Re-sending stops at the first success, including the node answering that it already holds the transaction (-27), at a node verdict, at a lookup that cannot run, and once the network has changed. A node's rejection of a re-send leaves the outcome unknown rather than `not_sent`, since the earlier attempt may have reached another node behind the same endpoint; a rejection of the first attempt still needs the absence probes before `not_sent`, as before. A re-send the guard refuses sends nothing and is looked up once more, so a transaction that landed meanwhile is reported as sent. A refused redirect, a 429, a missing route and a cancelled call are never re-sent. Whatever stays unknown keeps the existing reconcile path.
